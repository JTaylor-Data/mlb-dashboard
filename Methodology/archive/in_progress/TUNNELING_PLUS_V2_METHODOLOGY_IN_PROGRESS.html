1. Architecture — How v2 Differs from Live v3

The live Tunneling+ v3 is a single LightGBM regressor that predicts per-pitch delta_run_exp directly. v2 replaces that with the same five-classifier decomposed architecture used by Location+ v2:

  1. xSwing% — Will the batter swing on this pitch, given prior pitch context?
  2. xCS% — Given no swing, is it a called strike?
  3. xWhiff% — Given a swing, does the batter miss?
  4. xFoul% — Given contact, is it a foul?
  5. BIP type × EV distribution — 20-class multiclass for batted ball type and exit velocity

Same fixed run-value table (training/v2_artifacts/run_value_table.json) as Location+ v2 → per-pitch xRV → pitcher-season mean → plus-scale.

The key claim: framing the problem as five outcome classifiers (rather than one run-value regressor) is less susceptible to sign-flip artifacts from skewed run-value distributions.

2. Feature Set (28 Total)

Identical lag-context feature set to live Tunneling+ v3. The architecture change (classifiers vs. regressor) is what separates v2 from v3 — not the features.

Feature groupCountDetails
Lag features (×6 slots)24For each of lags 1–6: commit_distance, plate_distance, shape_break, pitch_type
Current-pitch categoricals4pitch_type, p_throws, stand, season

Lag distances explained:

  • lagN_commit_distance — distance between the current pitch and the Nth-prior pitch at this pitcher's commit point (~200ms before arrival) — the "tunneling window"
  • lagN_plate_distance — distance at the plate — where they actually separated
  • lagN_shape_break — how much the pair "popped apart early / tracked back late" — captures the deception arc

Missing lag slots (at-bat start, or beyond at-bat pitch count) are true NaN — never zero-filled. LightGBM handles natively. No pitch-type pair identity column exists — the model sees only sequential context, not "FF vs. CH".

3. Commit Point (Reused from v3)

For each pitcher-season: find the hardest FF/SI/FC by effective_speed, compute where it was 200ms before arriving using its real trajectory. That distance = the pitcher's commit point for the season.

v2 reads this from the same saved table v3 uses: training/tunneling_v2_artifacts/200ms/pitcher_season_commit_point.csv (9,348 pitcher-seasons). Not re-derived at scoring time.

5. ⚠ xCS% Pitch-Type Confound Finding

Finding (Part B of 2026-09-21 validation): The xCS% classifier partially exploits which pitch type was thrown as a proxy for called-strike probability — not entirely through tunneling signal. Ablating all pitch_type columns (current + all lag1–lag6 pitch_type columns) drops xCS% AUC from 0.7408 → 0.7127 (Δ = −0.028).

What this means:

  • ~96% of the xCS% signal (0.7127 / 0.7408) survives after removing pitch-type information entirely
  • ~4% is attributable to pitch-type identity being a proxy for CS probability (e.g., cutters get more called strikes than curveballs in certain counts)
  • The confound is real but modest — it does not invalidate the model
  • The remaining signal after ablation (0.713) is still meaningfully above 0.50 and comes from genuine lag-context tunneling features

Decision: Include pitch_type columns. The 4% confound is acceptable given that pitch type is a legitimate contextual signal (umpires' CS rates do vary by pitch type). Removing it would throw out real signal to avoid a small confound.
